## 一、架構核心思想

2026-09-26 局部新增資料流：`PlayerProfessionRuntime.OwnerPlayer → PlayerGrappleMomentumEnergy.NormalizedEnergy → BulletTracerLineDrawer`。Tracer 每發只讀動能滿值切換基礎色，維持本機表現，不介入權威傷害／充能；配置與驗證見 [50](50_武器瞄準與射擊.md)。

2026-09-19 Phase 4 前置-3 局部補充：HUD 只讀既有 Stage／SafeHouse Flow 與玩家動能倍率，左上固定三列，速度／傷害加成由既有 LocalPlayerSpeedSlider 在中下方呈現；小地圖僅建立空容器，無新 Gameplay 或網路擁有者。詳見 [146](146_PrePhase4-3_HUD排列與資訊精簡.md)。

目前專案已不是把所有功能都塞進 `Player` 或 `Enemy` 的原型階段，而是使用四層責任：

1. **輸入／意圖層**：玩家想做什麼，或 Enemy AI 選了什麼。
2. **規則／仲裁層**：現在是否允許做、哪個系統擁有移動或動作控制權。
3. **遊戲結果層**：State Authority 實際更新位移、傷害、生命、死亡與網路狀態。
4. **表現層**：動畫、相機、UI、LineRenderer、材質與聲音讀取結果呈現。

新增功能時應先決定它屬於哪一層。若一個新腳本同時採集輸入、直接扣血、播放動畫、移動角色並發 RPC，通常表示責任過度集中。

## 三、玩家 Prefab 的組裝觀念

`Player.cs` 應視為「組裝與更新協調根」，不是所有規則的唯一真相來源。玩家 Prefab 上的核心元件分工：

- `PlayerMovement`：KCC 輸入方向、速度、重力、跳躍與空中 Momentum。
- `PlayerStateMachine`：Grounded、Airborne、Grapple、Slide 等移動狀態語意。
- `PlayerSprintLatchController`：Shift 觸發跑步鎖定與加速累積。
- `PlayerSlideController`：蹲下、滑鏟、鈎索後寬鬆觸發、鏟跳。
- `PlayerGrapple`：鈎索生命週期與 GrappleAirborne。
- `PlayerActionGate`：能力與武器行為封鎖。
- `PlayerProfessionRuntimeManager`：只讓當前職業 Runtime 生效。
- `PlayerAbilityRuntimeManager`：維持獨立於職業切換的玩家能力 Loadout；驗證槽位、職業限制與互斥後，由 State Authority 生成能力 Runtime。
- `PlayerWeaponController`、`PlayerAimController`、`PlayerQuickActionController`：武器輸入的三個專責入口。
- `PlayerHealth`：玩家生命、傷害與死亡。
- `PlayerLocalView`：本機相機、第一人稱物件、效果與 UI 的啟閉。

## 四、Enemy Prefab 的組裝觀念

`EnemyActor` 是查找共同元件與定義的入口。Enemy 決策不是 Animator State Machine 主導，而是網路 AI 狀態驅動 Animator：

```text
AI / Combat State（真實遊戲狀態）
→ Animator Driver 設定參數
→ Animator 播放表現
```

因此動畫事件可作為視覺接點或回報攻擊接觸窗口，但不應讓 Animator 成為網路狀態的唯一真相。近戰揮砍目前由 `EnemyMeleeSwingAttack` 的武器碰撞／Damage Resolver 邏輯負責命中；Dash 則由 Dash 狀態中的 Hit Radius 接觸判定並防止同一目標重複傷害。

## 五、共用戰鬥協定的重要性

所有攻擊類型應產出一致的 `DamageRequest`，交由 `DamageReceiverUtility` 找到 `IDamageReceiver`。這樣才能統一：

- 正面／背面與 Hit Zone。
- 強制暴頭來源。
- Tank Guard 或其他傷害 Modifier。
- 攻擊者、受擊者與 NetworkObject 身分。
- 命中、暴頭、擊殺回饋優先序。
- 未來護甲、弱點、狀態效果與統計資料。

不要在武器內直接改 `PlayerHealth.CurrentHealth`，也不要讓 Enemy 攻擊另外建立一套扣血 API。

## 六、本地與世界表現邊界

本機第一人稱玩家需要更細的回饋，但其他玩家不需要全部聽見或看見：

- 本地：換彈拉槍機、ViewModel Animation Event、Movement Loop、HUD、第一人稱 Camera Shake。
- 世界：槍聲、會被其他玩家聽見的技能聲、Enemy 攻擊、NetworkObject 的狀態與位置。
- 兩者可能由同一事件觸發，但要分別送到 `GameplayAudioService` 與 `NetworkPlayerAudioEmitter`。

## 七、目前已知的結構風險

1. `PlayerGrapple.cs`、`AttackRifle.cs`、`SupportSMG.cs`、部分職業能力已很大，後續新增功能前先評估是否能抽成設定資料、Resolver 或 Presenter；不要繼續無限制堆疊。
2. `TestDamageReceiver` 已變成 Enemy 正式生命核心但名稱仍像測試物；未規劃完整遷移前不可直接重新命名，因 Prefab、序列化引用與多個系統都依賴它。
3. Attack Rifle 與 Support SMG 有大量相似射擊流程；未來若要抽共用基底，必須先列出差異（治療覆寫、特殊模式、彈藥規則），不可直接硬合併。
4. 第一人稱 Animator 讀 Networked 屬性前必須確認武器已 Spawn，職業切換尤其容易出現時序錯誤。
5. Enemy 的 Movement Ownership 是防止亂跑與互搶位移的關鍵。新增後退射擊、防禦或受控移動，都要先定義所有權。
6. 玩家能力已開始從職業 Runtime 拆成獨立 Loadout，但資產搬移由明確的 Editor 遷移選單執行；文件與除錯時必須分清楚「原始碼已支援」和「Prefab／Definition 已完成遷移」。
