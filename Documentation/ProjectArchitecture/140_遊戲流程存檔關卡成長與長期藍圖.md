# 遊戲流程、存檔、關卡循環與成長長期藍圖

> 狀態：**產品目標與分階段實作規格草案**  
> 建立日期：2026-09-17  
> 最後更新：2026-09-18（已固定 Host 存檔、失敗重設與全員 Ready；Phase 1-B Menu UI 已完成單機操作驗證）  
> 適用專案：`M:/UnityProject/Purgers`

## 1. 一句話遊戲循環

Host 從主選單建立或選擇本機存檔並開啟 Session，玩家進入獨立安全屋；Host 操作開始裝置並由所有玩家確認準備後進入目前關卡。完成撤離／擴充目標／Boss 目標後回到安全屋並提升關卡等級。限時結束或全員死亡則本輪失敗，清除本次循環成長並回到關卡等級 1；永久解鎖保留。

```text
_Menu
├─ Quick Play → 建立新存檔 → 安全屋
└─ 繼續遊戲 → 選擇存檔 → 安全屋

安全屋
└─ Host 靠近開始裝置 → 顯示「按 E 開始遊戲」→ E → 全員確認準備

遊戲關卡
├─ 一般關：完成撤離點等待 3 秒 + 額外目標
├─ Boss 關：擊敗 Boss（離場條件仍待確認）
├─ 成功：保存 Level + 1 → 回安全屋
└─ 失敗：清除循環成長、保存 StageLevel = 1 → 回安全屋
```

## 2. 名詞固定

為避免「關卡 Level」與「玩家 Level」混用，程式與文件固定使用以下名稱：

| 中文 | 建議程式名稱 | 意義 |
|---|---|---|
| 存檔 | `GameSave` / `SaveSlot` | 一次 Quick Play 建立的持久資料 |
| 永久進度 | `PermanentProgression` | 失敗後保留的永久點數、造型解鎖與安全屋天賦；目前僅為預留 |
| 循環進度 | `RunProgression` | 本次循環的關卡、玩家等級、經驗、獎勵、裝備、加成與 Debuff；失敗時清除 |
| 關卡等級 | `StageLevel` | 決定地圖數量、Boss 循環、時間與敵人基準；新存檔為 1 |
| 玩家等級 | `PlayerLevel` | 由擊殺經驗提升，用於獎池與裝備需求 |
| 關卡循環數 | `CycleLength` | 預設 4；每逢倍數關為 Boss 關 |
| 循環內階段 | `CycleStage` | `((StageLevel - 1) % CycleLength) + 1` |
| 新增 Chunk 數 | `AdditionalChunkCount` | 一般關預設為 `CycleStage - 1` |
| 撤離點 | `ExtractionPoint` | 一般關最後一個 Chunk 中抽選的指定地點 |
| 升級所需經驗 | `BaseExperienceRequirement` | 預設 10 |
| 升級級距 | `ExperienceGrowthMultiplier` | 預設 2 |

預設 `CycleLength = 4` 時：

| StageLevel | CycleStage | 類型 | 新增 Chunk |
|---:|---:|---|---:|
| 1 | 1 | 一般關 | 0 |
| 2 | 2 | 一般關 | 1 |
| 3 | 3 | 一般關 | 2 |
| 4 | 4 | Boss 關 | 由 Boss 規則決定 |
| 5 | 1 | 一般關 | 0 |
| 6 | 2 | 一般關 | 1 |
| 7 | 3 | 一般關 | 2 |
| 8 | 4 | Boss 關 | 由 Boss 規則決定 |

## 4. 存檔責任

### 4.1 Host 單一存檔

- 存檔只存在 Host 本機，Host 是唯一可建立、載入與寫回 `GameSave` 的端點。
- Quick Play 固定建立一份新存檔，完成首次原子寫入後以 Host 身分建立全新的 Fusion Session。
- 繼續遊戲先由 Host 選擇本機存檔，再以該存檔開啟 Session。
- Client 只透過 Party Menu 加入 Session；Client 不建立、不選擇，也不直接寫入存檔。
- Client 遊戲中需要顯示的關卡與成長資料，由 Host 的權威 Runtime State 同步；不得讓 Client 以本機檔案覆蓋 Host 狀態。
- Phase 1 不做 Host Migration。Host 離線時 Session 結束，保留最後一次已成功提交的安全屋狀態；是否把中途離線視為失敗仍需另行決定。

### 4.2 存檔不是遊戲場景快照

離開遊戲時只保存可重建的長期狀態，不保存每隻 Enemy、每顆子彈、每個 Chunk Transform 或玩家離開瞬間的位置。

再次載入存檔時一律進入該 `StageLevel` 的安全屋，由安全屋重新開始下一次關卡。

### 4.3 最小存檔資料

```text
SaveVersion
SaveId
DisplayName
CreatedUtc
LastPlayedUtc
CycleLengthSnapshot 或規則版本
PermanentProgression（目前只預留資料邊界）
  ├─ PermanentPoints
  ├─ CosmeticUnlockIds
  └─ SafeHouseTalentIds
RunProgression
  ├─ StageLevel
  ├─ PlayerProgressionEntries
  │   ├─ StablePlayerId（多人持久化規則確定後使用；不可保存 PlayerRef）
  │   ├─ PlayerLevel
  │   ├─ CurrentExperience
  │   ├─ 本循環取得的角色加成
  │   ├─ 已裝備的 GrappleHit / GrappleFocus / Weapon
  │   ├─ 持有裝備與需求等級
  │   └─ Debuff / 一次性能力狀態
  └─ 本循環其他可重建狀態
```

目前沒有永久解鎖內容。第一版只建立清楚的 `PermanentProgression` 邊界與預設空資料，不先實作永久點數取得、造型商店或安全屋天賦效果。未來的例子包含不死圖騰，以及提高升級獎勵品質並降低或移除懲罰的天賦。

存檔必須具有：

- `SaveVersion` 與遷移入口，避免日後欄位增加後舊檔無法載入。
- 穩定 ID；能力、武器、角色加成與 Debuff 不保存 Unity Object 名稱或 Instance ID。
- 暫存檔寫入成功後再取代正式檔，避免程式中止造成整份存檔損壞。
- 建立、列出、讀取、更新、刪除彼此分離的 Repository API。
- Menu 顯示資料與完整 Gameplay 資料分離，避免為了顯示清單就載入所有內容。

### 4.4 寫檔時間點

- Quick Play 建立新檔成功時。
- 選擇獎勵或改變持久裝備後。
- 關卡成功並將 `StageLevel + 1` 後，回安全屋前。
- 關卡失敗並完成重設後，回安全屋前。
- 安全屋購買／升級完成時。

遊戲中途退出只保存最近一次已提交狀態；不保存戰鬥場景現況。

## 5. Menu 與存檔選擇

### 5.1 Quick Play

目標行為：

1. 建立新的唯一 `SaveId`。
2. 初始化 `StageLevel = 1`、`PlayerLevel = 1` 與預設裝備。
3. 完成寫檔後，將此檔設為目前 Session 使用的存檔。
4. 明確以 Host 身分建立新的 Fusion Session，不使用可能加入既有房間的 `AutoHostOrClient` 語意。
5. 載入安全屋，而不是直接載入戰鬥 Game Scene。

`MenuConnection` 現在把空 Session 且 `Creating=false` 明確辨識為 `QuickPlayNewHost`，不再使用 `AutoHostOrClient`。建立新存檔成功後才啟動 Host；若開房失敗，刪除這次尚未啟用的新檔。Party Menu 的明確 Client Join 只進入 ReadOnly Context；Party Create 在沒有已選 Host 存檔時也建立新檔。

### 5.2 繼續遊戲

在 `_Menu` 的 Quick Play 右側新增「繼續遊戲」按鈕。按下後顯示位於 Menu Canvas 最上層的存檔選擇 Overlay。

最小 Overlay：

- 可捲動存檔清單。
- 每列顯示名稱、StageLevel、PlayerLevel、最後遊玩時間。
- 選取後顯示「開始」與「返回」。
- 沒有存檔時顯示明確空狀態。
- 刪除／重新命名先保留擴充點，不列入第一個可玩版本，除非另行確認。

不得直接修改 Fusion 套件內建 View；應由專案自己的 Menu Save Controller 包裝現有 Quick Play／Connect 流程。

## 6. 安全屋

安全屋是獨立 Unity Scene，不是 Game Scene 裡的一棟建築。

安全屋第一階段只需要：

- 玩家可移動的安全區。
- 出生點。
- 開始遊戲互動裝置。
- World Space Canvas + TMP 提示「按 E 開始遊戲」。
- 顯示目前 StageLevel 的 HUD。

開始裝置契約：

1. 玩家進入互動範圍後，本地顯示提示。
2. 離開範圍立即隱藏。
3. 只有 Host 可按 E 發起 Ready Check；這次 E 不直接切換場景。
4. Ready Check 開啟後，每位目前在 Session 內的玩家都必須各自確認準備，包含 Host。
5. Client 的確認只送出一次請求，由 State Authority 驗證玩家身分、目前流程狀態與重複提交。
6. State Authority 同步每位玩家的 Ready 狀態；尚未全員 Ready 時不得開始載入關卡。
7. 全員 Ready 後鎖住重複互動，才開始 Fusion 場景轉換。

中途加入、Ready Check 期間離線、取消準備與逾時規則尚未決定；在規則確定前，不把這些邊界行為藏在 UI 或單一互動腳本裡。

不得由 Client 直接呼叫普通 `SceneManager.LoadScene` 決定正式 Gameplay Scene；多人 Scene 轉換需經目前 Runner／NetworkSceneManager 的權威流程。

## 7. 關卡狀態機

建議狀態：

```text
None
→ SafeHouse
→ LoadingStage
→ StageActive
→ StageSuccessPending
→ ReturningToSafeHouse

StageActive
→ StageFailedPending
→ ReturningToSafeHouse
```

所有會改變結果的狀態只由 State Authority提交：

- StageLevel 與規則快照。
- 地圖 Seed 與 Chunk 拓撲。
- 目標進度。
- 倒數時間。
- Boss 是否死亡。
- 關卡成功／失敗。
- 成功提升 StageLevel 或失敗重設。

HUD 只讀取權威快照，不自行判定勝負。

## 8. 地圖生成與 StageLevel

### 8.1 一般關

```text
CycleStage = ((StageLevel - 1) % CycleLength) + 1
AdditionalChunkCount = CycleStage - 1
```

- `CycleStage = 1`：只使用起始 Chunk，不接第二 Chunk；四個未接合 Connector 都應由阻擋屋封閉。
- `CycleStage = 2`：起始 Chunk + 1 個生成 Chunk。
- `CycleStage = 3`：起始 Chunk + 2 個生成 Chunk。
- 後續 Chunk 不可選擇指回上一個 Chunk 的接合方向。
- 實作第三 Chunk 前必須加入拓撲記錄、Bounds／Collider 重疊拒絕、失敗重抽上限與可重現 Seed。
- Client 必須依 Host 同一份拓撲資料重建或接收網路生成結果。

### 8.2 Boss 關

`StageLevel % CycleLength == 0` 時為 Boss 關。

Boss 關的地圖來源、是否仍生成一般 Chunk、是否需要撤離點仍待決定。第一版應透過 `StageRuleDefinition` 覆寫，不把 Boss 判斷散落在地圖、Enemy 與 UI 腳本。

### 8.3 撤離點

- 每個 MapChunk 可配置多個候選 `ExtractionPoint`。
- 一般關只從最後一個 Chunk 的候選點抽一個。
- StageLevel 1 的起始 Chunk同時也是最後 Chunk，因此從起始 Chunk 抽選。
- 抽選由 Host 使用本輪 Seed 決定，Client 只接收結果。
- 撤離點必須有可到達性與占用驗證，不能只靠 Transform 存在。

## 9. 關卡目標

目標系統使用可組合定義，不在關卡管理器內寫死大量 `if level == ...`。

第一個必要目標：

```text
ReachExtractionAndHoldObjective
├─ 進入指定撤離區
├─ 必須持續停留 3 秒
├─ 中途離開則中斷或重設（待確認）
└─ 完成後回報 State Authority
```

可擴充目標：

- 擊殺指定數量 Enemy。
- 清除指定區域。
- 啟動裝置。
- 攜帶物品抵達撤離點。
- 保護目標。
- 擊敗 Boss。

Boss 關至少需要 `DefeatBossObjective`。目標集合應支援 `All`／`Any` 組合，第一版一般關使用所有必要目標均完成。

## 10. 關卡計時與失敗

- 關卡進入 `StageActive` 後才開始倒數。
- `StageRuleDefinition` 可設定秒數或 Unlimited。
- 時間由 State Authority 推進並同步剩餘時間。
- 倒數歸零且尚未提交成功：關卡失敗。
- 全員生命值歸零：關卡失敗。
- 成功與失敗必須只有一個原子提交入口，避免同 Tick 同時完成撤離又全滅。
- 失敗後清除 `RunProgression`，以 `StageLevel = 1`、`PlayerLevel = 1`、零經驗與預設循環裝備重新建立，再返回安全屋。
- 本次循環取得的裝備、角色加成、Debuff、一次性能力與其他關卡內成長一併清除。
- `PermanentProgression` 必須保留；未來永久點數、造型解鎖與安全屋天賦均不得被一般關卡失敗覆寫。
- 永久天賦若會提供開局效果，應在新的 `RunProgression` 建立後重新套用，不能把效果結果混存成永久基礎數值。

目前尚未實作任何永久解鎖或永久點數。這些欄位在第一版保持空值／零值，不因此提前建立商店或天賦系統。

## 11. Enemy Level 與屬性縮放

Enemy Level 選擇模式：

```text
Fixed
StageRelativeRandomRange
```

`StageRelativeRandomRange`：

```text
EnemyLevel = max(1, StageLevel + RandomInclusive(MinOffset, MaxOffset))
```

例如 `StageLevel = 6`、Offset `-5..+5`，可以抽到 Enemy Level 9。

每一項 Enemy 屬性可分別設定：

```text
Fixed
BasePlusPerLevel
```

線性第一版公式：

```text
FinalHealth = BaseHealth + HealthPerLevel × (EnemyLevel - 1)
FinalMoveSpeed = BaseMoveSpeed + MoveSpeedPerLevel × (EnemyLevel - 1)
FinalDamage = BaseDamage + DamagePerLevel × (EnemyLevel - 1)
```

生成時由 State Authority 算出 Enemy Level 與最終數值，Enemy 不直接在各自攻擊腳本中讀取 StageLevel。這保留固定 Enemy、Boss 特規與日後曲線資產的空間。

## 12. 玩家經驗與三選一獎勵

### 12.1 經驗

- 新存檔 `PlayerLevel = 1`。
- 擊殺 Enemy 獲得等同 `EnemyLevel` 的經驗。
- 第一個升級需求預設 10。
- 下一級需求乘上 `ExperienceGrowthMultiplier`，預設 2。

建議公式：

```text
RequiredExperience(PlayerLevel)
= BaseExperienceRequirement × ExperienceGrowthMultiplier^(PlayerLevel - 1)
```

超額經驗保留到下一級；一次獲得大量經驗時允許連續升級，但每次升級獎勵需要依序處理。

### 12.2 獎勵池

每次升級從以下分類抽三個互不重複候選：

- Grapple Hit 能力。
- Grapple Focus 能力。
- Weapon。
- 角色加成。
- 一次性特殊能力。
- 未來新增分類。

每個獎勵 Definition 至少包含：

```text
StableRewardId
Category
MinimumPlayerLevel
Weight
RepeatPolicy
Runtime／Definition References
```

Grapple Hit、Grapple Focus、Weapon 若玩家等級低於 `MinimumPlayerLevel`，正常情況不進入獎池。

### 12.3 越級獎勵與 Debuff

- 預設 25% 可調機率出現越級候選。
- 越級範圍可調。
- 玩家選擇越級候選後，同時取得一個相容 Debuff。

Debuff 應使用可擴充 Definition／Runtime，而非獎勵 UI 直接寫效果。預計分類：

- 負面角色屬性。
- 完成指定擊殺數前無法重抽／回寫／替換的限制。
- 受擊後緩速。
- 受擊後暈眩機率或持續時間。
- 可清除與不可清除標記。

25% 是每次升級是否注入一個越級候選、還是每個候選各自判定，仍待確認。

## 13. 可替換裝備與世界掉落

可替換裝備包含：

- Grapple Hit。
- Grapple Focus。
- Weapon。

替換規則：

1. 新裝備通過需求等級與槽位驗證。
2. 舊裝備生成為權威 Network Loot Object，掉落在玩家附近安全位置。
3. 玩家可主動丟棄。
4. 其他玩家可撿拾。
5. 玩家等級低於裝備需求時拒絕撿取，物件留在世界。

掉落物保存到安全屋／下一關與否仍待確認。第一版建議戰鬥場景掉落只存在該次關卡，持有並裝備成功後才寫入存檔。

## 14. Profession 移除的遷移原則

長期目標是讓 Weapon 與能力直接決定玩法，不再讓 Attack／Support／Tank Profession 擁有整組武器。

以下既有 Gameplay 必須保留：

- Tank Guard。
- Tank Melee Combo。
- Tank Quick Dash。
- Attack Aim、Attack Rifle、Attack Quick Melee。
- Support Aim、Support SMG、Support Melee。
- 現有傷害、動畫、音效、Action Gate 與 ViewModel 接線。

遷移順序：

1. 為 Weapon／Quick Action／Passive 建立不依賴 Profession Enum 的穩定 Definition 與 Runtime 契約。
2. 以相容 Adapter 讓現有 Profession Runtime 仍可提供舊內容。
3. 存檔與獎勵開始保存裝備 Stable ID。
4. ViewModel、輸入與 HUD 改讀目前裝備。
5. 所有三套內容均可獨立裝備並完成多人驗證後，才移除 Profession 選擇與舊路由。

禁止先刪除 `PlayerProfession` 再逐支救回依賴程式；這會同時破壞 Spawn 初始化、Runtime Prefab、武器路由與 ViewModel。

## 15. 角色加成

第一批角色加成：

- 基礎輸出傷害加成。
- 最大生命值加成。
- 回復量加成。
- 鈎索能量消耗降低。
- 未來擴充。

基礎傷害加成應進入共用 Damage Modifier 管線，與速度動能增傷依明確順序組合，不讓每把武器各自重寫倍率。

建議診斷顯示：

```text
Base Requested Damage
Character Bonus
Speed Momentum Bonus
Other Modifiers
Final Requested Damage
```

## 16. 新鈎索能量規則

目標規則：

- 每次符合消耗條件的鈎索使用消耗 1 點能量。
- 能量耗盡後必須在場景補充點恢復。
- 不使用一般時間 CD。
- 前一次鈎索未完整釋放前不能再次發射，防止連按彈跳。
- 玩家本次移動距離不超過 5 時不消耗能量。
- 角色加成可降低消耗。

必須先定義「移動距離」的量測起終點、傳送／被拉／滑鏟是否計入，以及減耗後如何處理非整數消耗。這些決定前不應直接替換現有職業充能／冷卻資料。

## 17. 遊戲內 HUD

以目前速度傷害增益 Debug HUD 的即時可視化方式為參考，建立獨立 `RunStatusHUD`，至少顯示：

- Save 顯示名稱或短 ID。
- StageLevel、CycleStage、一般／Boss。
- 目前 Chunk 進度。
- 關卡目標與撤離等待進度。
- 剩餘時間或 Unlimited。
- PlayerLevel、目前／需求經驗。
- 鈎索能量。
- 開發模式下的 Enemy Level 與縮放結果。

正式 HUD 與開發診斷可以共用唯讀 Snapshot，但不要讓 UI 直接修改關卡或玩家資料。

## 18. 建議系統邊界

| 系統 | 職責 |
|---|---|
| `SaveRepository` | 檔案列出、建立、讀取、原子寫入、刪除、版本遷移 |
| `ActiveSaveContext` | 目前選中存檔與未提交／已提交狀態 |
| `LevelCycleRules` | CycleLength、Boss 判定、Chunk 數量與時間規則 |
| `RunFlowDirector` | 安全屋／Loading／Stage／成功／失敗狀態機 |
| `StageObjectiveDirector` | 組合與仲裁目標，不直接生成地圖 |
| `MapGenerationDirector` | 依權威規格與 Seed 建立 Chunk 拓撲與撤離點 |
| `EnemyLevelResolver` | 算出 Enemy Level |
| `EnemyStatResolver` | 由 Enemy Level 與 Definition 算最終屬性 |
| `PlayerProgression` | PlayerLevel、經驗、待處理升級 |
| `RewardDraftDirector` | 三選一、越級候選與 Debuff 配對 |
| `EquipmentInventory` | 持有、裝備、需求驗證與 Stable ID |
| `WorldLootService` | 權威掉落、丟棄與撿拾 |
| `GrappleEnergy` | 能量、消耗、免消耗判定與補充 |

ScriptableObject 保存設計規則與 Definition；玩家進度、關卡狀態與存檔內容使用可序列化 Runtime Data，不直接修改 ScriptableObject 資產。

## 20. 已定決策與待確認問題

### 20.1 已定決策（2026-09-18）

1. **Host 單一存檔**：Host 建立、選擇及寫回存檔；Client 經 Party Menu 加入且不建立、不寫入存檔。
2. **Quick Play 網路語意**：每次固定建立新存檔與新 Host Session；繼續遊戲由 Host 選檔後開房。
3. **失敗重設範圍**：保留永久解鎖，清除本次循環取得的成長。目前永久系統未實作，只預留永久點數、造型與安全屋天賦資料邊界。
4. **安全屋多人開始條件**：Host 按 E 發起，包含 Host 在內的每位玩家都確認 Ready 後才進入關卡。

### 20.2 尚待確認

1. **撤離條件**：一名玩家等待 3 秒、所有存活玩家、全隊所有玩家，或允許倒地者被拋下？
2. **Boss 關地圖**：獨立 Boss Scene、專用 Chunk Prefab，或仍使用一般生成地圖？擊敗 Boss 後是否還需撤離？
