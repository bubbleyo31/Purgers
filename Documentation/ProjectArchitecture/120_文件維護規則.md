# 架構文件維護規則

> 目標：讓不同 ChatGPT 對話與未來的自己，不會拿過期文件覆蓋新版架構。

## 1. 原始碼永遠是最終真相

文件是索引與設計意圖，不是編譯器。若文件與 `Assets/Scripts` 不一致：

1. 先以目前原始碼確認真實行為。
2. 指出是哪份文件發生漂移。
3. 完成功能修改後，同一批次修正文檔。
4. 不可為了迎合舊文件而把正確的新程式改回去。
5. 明確區分「原始碼已實作」、「Editor 遷移工具已提供」、「Prefab／資產已實際遷移」與「Play Mode 已驗證」，不可把前一階段描述成後一階段。

## 2. 哪些改動必須更新文件

以下任一項成立就必須更新：

- 新增、刪除、重新命名或移動 C#。
- 類別的單一職責改變。
- 新增或移除跨系統引用。
- 變更 State Authority／Input Authority／本地 Render 責任。
- 新增 RPC、Networked 欄位、Network Prefab 或 Scene NetworkObject。
- 改變輸入到結果的資料流。
- 改變 Action Gate、Movement Ownership、狀態機或優先級。
- 改變 Prefab 必備元件或 Inspector 掛載位置。

只改 Tooltip、註解、私有常數且不影響行為時，可以只更新最後核對日期，不必改架構圖。

## 3. 修改對照表

| 改動 | 必須同步更新 |
|---|---|
| 任一 C# 新增／刪除／改職責 | `02_程式職責總表.md` + 對應模組文件 |
| 跨大系統資料流 | `00_CHATGPT快速讀取.md` + `01_專案架構總覽_給開發者.md` + 兩側模組文件 |
| 玩家核心／職業入口 | `20`、`40`，必要時 `00` |
| 鈎索路由或 Receiver | `30`，若影響職業再改 `40` |
| 能力分類、槽位、Definition、Loadout 或 Ability Runtime | `41` + `40`，若改變玩家主資料流再改 `00` |
| DamageRequest／Health API | `60` + 所有呼叫方模組 |
| Enemy 狀態、鎖、移動所有權 | `90` + `91` |
| ViewModel／動畫參數 | `70`，若讀武器狀態再改 `50` |
| Audio Delivery 規則 | `80`，若新增事件來源也改該來源模組 |
| HUD 資料介面 | `100` + 資料來源模組 |

## 4. 每份文件的固定頁首

更新文件時保留：

```text
最後核對日期：YYYY-MM-DD
核對來源：Assets/Scripts/...
相關文件：...
```

若只核對了部分檔案，要明寫「局部核對」，不能把日期更新成像是全專案已驗證。

## 5. ChatGPT 在新對話的更新流程

```text
讀 00 快速文件
→ 讀任務所屬模組
→ 搜尋實際類別與公開介面
→ 比較文件是否漂移
→ 修改程式
→ 編譯／測試
→ 更新職責總表與模組文件
→ 若跨模組，再更新快速文件與總覽
```

## 6. 文件版本紀錄

每次結構性修改，在被影響文件底部加入一筆：

```text
## 變更紀錄
- 2026-09-14：建立第一版架構基線；來源為 140 支 C#。
```

只記錄結構性改動，不要把每次數值微調都寫進來，否則文件會失去可讀性。

## 7. 禁止事項

- 不建立第二份內容相同但名稱不同的總覽。
- 不複製整段 C# 到架構文件；文件應說明責任、介面與連結。
- 不把暫時 Debug 行為寫成正式架構保證。
- 不在未核對原始碼時宣稱文件已更新至最新版。
- 不因檔名含 `Test` 就自動判定可以刪除。
