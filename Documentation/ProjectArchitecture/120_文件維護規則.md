# 架構文件維護規則

> 目標：讓不同 ChatGPT 對話與未來的自己，不會拿過期文件覆蓋新版架構。

## 1. 原始碼永遠是最終真相

文件是索引與設計意圖，不是編譯器。若文件與 `Assets/Scripts` 不一致：

1. 先以目前原始碼確認真實行為。
2. 指出是哪份文件發生漂移。
3. 完成功能修改後，同一批次修正文檔。
4. 不可為了迎合舊文件而把正確的新程式改回去。
5. 明確區分「原始碼已實作」、「Editor 遷移工具已提供」、「Prefab／資產已實際遷移」與「Play Mode 已驗證」，不可把前一階段描述成後一階段。

## 2. 哪些改動必須更新文件

以下任一項成立就必須更新：

- 新增、刪除、重新命名或移動 C#。
- 類別的單一職責改變。
- 新增或移除跨系統引用。
- 變更 State Authority／Input Authority／本地 Render 責任。
- 新增 RPC、Networked 欄位、Network Prefab 或 Scene NetworkObject。
- 改變輸入到結果的資料流。
- 改變 Action Gate、Movement Ownership、狀態機或優先級。
- 改變 Prefab 必備元件或 Inspector 掛載位置。

只改 Tooltip、註解、私有常數且不影響行為時，可以只更新最後核對日期，不必改架構圖。

## 3. 修改對照表

| 改動 | 必須同步更新 |
|---|---|
| 任一 C# 新增／刪除／改職責 | `02_程式職責總表.md` + 對應模組文件 |
| 跨大系統資料流 | `00_CHATGPT快速讀取.md` + `01_專案架構總覽_給開發者.md` + 兩側模組文件 |
| 玩家核心／職業入口 | `20`、`40`，必要時 `00` |
| 鈎索路由或 Receiver | `30`，若影響職業再改 `40` |
| 能力分類、槽位、Definition、Loadout 或 Ability Runtime | `41` + `40`，若改變玩家主資料流再改 `00` |
| DamageRequest／Health API | `60` + 所有呼叫方模組 |
| Enemy 狀態、鎖、移動所有權 | `90` + `91` |
| ViewModel／動畫參數 | `70`，若讀武器狀態再改 `50` |
| Audio Delivery 規則 | `80`，若新增事件來源也改該來源模組 |
| HUD 資料介面 | `100` + 資料來源模組 |

## 4. 每份文件的固定頁首

更新文件時保留：

```text
最後核對日期：YYYY-MM-DD
核對來源：Assets/Scripts/...
相關文件：...
```

若只核對了部分檔案，要明寫「局部核對」，不能把日期更新成像是全專案已驗證。

## 5. ChatGPT 在新對話的更新流程

```text
讀 00 快速文件
→ 涉及功能時，先搜尋關鍵詞規則索引（含別名／類名）
→ 讀命中的正式規則與設定
→ 添加功能但索引與相關文件仍找不到：先詢問是否為新功能並等待答覆
  → 否：先深入查專案文檔／歷史規劃，再追查實作；仍找不到則請使用者提供線索，不重建
  → 是：依既有架構規劃新增
  → 未答覆：只做唯讀或不依賴此判定的工作，不先實作新系統
→ 讀任務所屬模組
→ 搜尋實際類別與公開介面
→ 比較文件是否漂移
→ 修改程式
→ 編譯／測試
→ 更新職責總表與模組文件
→ 若跨模組，再更新快速文件與總覽
→ 打磨完成後提出具體索引條目，詢問是否收錄／更新；已明確授權則直接同步
```

## 6. 文件版本紀錄

每次結構性修改，在被影響文件底部加入一筆：

```text
## 2026-09-17 局部核對與架構補充

程式變更後執行 PurgersRegression EditMode 測試並確認實際測試數大於零；MCP 回傳 succeeded 但 total=0 不算驗證。結果與多人測試邊界記於 [130](130_回歸驗證與審查狀態.md)。

## 變更紀錄
- 2026-09-14：建立第一版架構基線；來源為 140 支 C#。
```

只記錄結構性改動，不要把每次數值微調都寫進來，否則文件會失去可讀性。

## 7. 禁止事項

- 不建立第二份內容相同但名稱不同的總覽。
- 不複製整段 C# 到架構文件；文件應說明責任、介面與連結。
- 不把暫時 Debug 行為寫成正式架構保證。
- 不在未核對原始碼時宣稱文件已更新至最新版。
- 不因檔名含 `Test` 就自動判定可以刪除。

## 8. 關鍵詞索引的收錄與維護

入口為 [關鍵詞規則索引](關鍵詞規則索引.md)。它保存搜尋詞、精簡規則與正式設定的連結，不建立第二份完整規格或平衡數值表。

1. 新對話涉及功能新增、修改或打磨時，搜尋名稱、同義詞與類名；先讀命中的規則，再核對現行程式與必要資產。多個命中都要辨識，不可只採第一筆。添加功能但索引與相關文件仍找不到時，必須先詢問是否為新功能；若否，先深入查專案文檔、歷史規劃與設定／驗證紀錄，再核對實作與必要資產；仍找不到便回報搜尋範圍並請使用者提供線索，不自行重建。若是，依既有架構規劃新增。未答覆前僅做唯讀或不依賴該判定的工作，不把沉默當成新功能確認；已明確回答過則不重複問。詳細分支見索引「找不到功能時的必要確認」。
2. 功能或規則打磨完成後，主動提出可審閱的條目：建議關鍵詞／別名、定案摘要、正式規則及設定位置、實作與驗證邊界，並詢問使用者是否加入或更新索引。已有明確收錄授權時直接完成；未回覆不等於同意，也不可反覆追問或停止其餘已授權工作。
3. 使用者確認後，在同一批文件變更新增或更新條目；先檢查既有 ID／別名，避免同一規則分裂成多份。規則正文若尚未保存，先記入對應模組文件，再由索引連結過去。
4. 已收錄條目遇路徑搬移、實作或驗證狀態改變，依既有文件維護義務同步校正；這類事實維護不需重複徵求收錄許可。新增設計或改寫定案內容仍按第 2 點確認。
5. 各條目分開標記規則狀態、實作／資產狀態與驗證狀態。原型參數、未決事項及舊版規則必須明確註記；已規劃不等於已實作，程式存在也不等於已接線或已驗收。
6. 核對日期只覆蓋實際查閱的範圍；不得因新增索引而宣稱重跑 Unity 編譯、回歸、Play Mode 或 Host／Client。索引與原始碼不一致時指出漂移，依第 1 節處理，不為迎合歷史文件回退程式。
